# 0022. 여러 작업을 병렬로 진행한다 — 창 하나 = 작업 하나, 작업별 기록·타임라인

- 상태: 확정
- 날짜: 2026-11-18
- 출처: 261118-parallel-tasks plan-v2 (§3 B~E)

## 맥락

서버는 활성 작업 하나만(`State.activeTask`)가졌기 때문에 다른 프로젝트의 작업은 하나씩만 진행할 수 있었다. 사용자 요청(D2, D5, D9, D10, D13, D14): 서버가 작업을 여러 개 동시에 갖고, UI 창 하나는 작업 하나만 처리하며, 기록·타임라인도 작업별로 분리한다.

## 결정

- **여러 작업 동시 보유**(D9, D10): `State.tasks: Record<string, Task>`(작업 ID `t-<YYYYMMDD-HHmmss>-<hex4>`). 동시 작업 수 제한 없음. 같은 프로젝트에 폴더가 정해지지 않은(`folder === null`)새 작업은 하나뿐 — 두 번째는 409.
- **창 하나 = 작업 하나**(D2, D5): 창 URL `?task=<id>`. 없으면 시작 화면 — 새 작업을 만들거나, 창이 붙지 않은 진행 중 작업(`unattached`)을 골라 이어서 본다. 작업 화면은 자기 작업에 배정된 세션·기록만 보고 다른 작업의 정보는 알지 못한다.
- **작업별 기록**(D13): `state/tasks/<id>/events.jsonl`. 세션 전환 등 배정 안 된 세션의 이벤트는 전역 `state/events.jsonl`로.
- **작업별 SSE**: 작업 채널(그 작업의 `state`·`notify`) + lobby 채널(시작 화면 — `unattached` 목록). 알림은 그 작업의 창에만.
- **다시 붙기**(D14): 같은 작업에 새 창으로 다시 붙으면 지난 기록도 보인다.

## 결과

- 토스트 메시지에 `[<project>/<folder 또는 "새 작업">] ` 접두어가 붙어 어떤 작업인지 알 수 있다.
- 작업을 종료하면 그 작업만 삭제되고, 배정 세션은 allow로 해제된다.
- 1단계와 2단계 사이의 한계: 같은 프로젝트의 두 작업이 CODER를 동시에 돌리거나, 두 작업이 같은 로컬 엔드포인트를 동시에 쓰는 것을 서버가 막지 않는다 — 사용자가 피한다.
- 2단계(다음 작업): 로컬 모델 대기열(D3), 프로젝트별 코딩 잠금(D4, D6, D7, D11), "순서 대기" 배지(D8).

## 검토한 대안

- **UI 하나에 모든 작업 목록**: D2(창 하나 = 작업 하나)로 기각.
- **이벤트를 전역 파일 하나에 `task` 필드로 구분**: D13(작업별 파일)로 기각.
- **작업 ID를 쿠키·localStorage로**: 창마다 달라야 하고 새로고침·재연결에 남아야 하므로 URL 쿼리가 가장 단순.
